# BLE: сопряжение клиентов (HUD, камера) с устройствами (сниффер, шлюз, проигрыватель)

Действует начиная с прошивок: **сниффер 2.8.0** (обе платы), **шлюз 1.2.0**, **проигрыватель 1.1.0**.
Работает вместе с протоколом потока кадров ([BLE_ACL_protocol_ru.md](BLE_ACL_protocol_ru.md)): сначала сопряжение, потом ACL.

> **Что менять в чате HUD:** прошивка HUD должна уметь сопрягаться по коду доступа (раздел 2) и обрабатывать отказы (раздел 4). Без этого при включённой защите HUD не получит ни одного кадра.

## 1. Как устроена защита

- **Включается кодом в `secrets.h` устройства:** `BLE_PASSKEY` — шесть цифр. `0` — защита выключена, доступ открыт всем, как в прежних версиях (в этом режиме HUD работает как раньше и ничего менять не нужно).
- **Один и тот же код** прописывается в `secrets.h` устройства и в `secrets.h` HUD. Файл `secrets.h` в репозиторий не публикуется (`.gitignore`), в репозитории лежит только шаблон `secrets.example.h`.
- **Тип сопряжения:** LE Secure Connections, с защитой от перехвата (MITM) и запоминанием ключей (bonding). Устройство заявляет *DisplayOnly* («показываю код»), клиент — *KeyboardOnly* («ввожу код»). Человек код не вводит: клиент подставляет константу из своей прошивки.
- **Один клиент на устройство («слот»).** Пока клиент сопряжён, новые сопряжения не принимаются: вместо настоящего кода устройство выдаёт случайный, и сопряжение любого нового клиента не удаётся. Запомненный клиент входит по сохранённым ключам, код ему не нужен.
- **Одно соединение.** Пока клиент подключён, устройство не рекламируется; если всё же подключится второй, его сразу отключают. Камера и HUD одновременно к одному устройству не подключаются.
- **Время на сопряжение:** клиент, не прошедший его за **15 с** после подключения, отключается. **5 неудач подряд** — сопряжение блокируется на **60 с** (это касается только нового сопряжения, пока слот свободен).
- **До сопряжения** подписки на уведомления (`…0002`, `…0008`) и запись (`…0004`, `…0007`) отклоняются. Подписываться нужно **после** шифрования канала.
- **Сброс сопряжений:** удержание кнопки **BOOT 5 с на работающем устройстве** (раздел 5).

## 2. Что должен делать клиент

Порядок:

1. Инициализация и настройки безопасности (до подключения).
2. Поиск устройства по имени `S3-CAN-Sniffer` (и/или по UUID сервиса).
3. Подключение.
4. `secureConnection()` — выполнит сопряжение (запросит код, клиент подставит его) или шифрование по сохранённым ключам.
5. **Проверить**, что канал зашифрован **и аутентифицирован** (`isEncrypted() && isAuthenticated()`). Если нет — отключиться: это значит, что сопряжение прошло без кода (Just Works), то есть вы говорите не с тем устройством.
6. Только теперь: подписка на `…0008` (камера — на `…0002`), запись списка ACL в `…0007`.
7. При обрыве — переподключение с паузой (раздел 4).

Параметры клиента:

- `NimBLEDevice::setSecurityAuth(true, true, true)` — bonding, MITM, Secure Connections;
- `NimBLEDevice::setSecurityIOCap(BLE_HS_IO_KEYBOARD_ONLY)`;
- `NimBLEDevice::setMTU(247)` — до подключения (для крупных пачек кадров);
- код `BLE_PASSKEY` — из `secrets.h` HUD, тот же, что в устройстве.

### Пример (NimBLE-Arduino 2.x)

Сигнатуры сверены с заголовками библиотеки и её примером `NimBLE_Client`.

```cpp
#include <NimBLEDevice.h>
#include "secrets.h"                       // BLE_PASSKEY — тот же, что в устройстве

static volatile bool g_secured = false;

class PairCb : public NimBLEClientCallbacks {
  // Устройство "показывает" код, клиент "вводит" — подставляем константу
  void onPassKeyEntry(NimBLEConnInfo& connInfo) override {
    NimBLEDevice::injectPassKey(connInfo, BLE_PASSKEY);
  }
  void onAuthenticationComplete(NimBLEConnInfo& connInfo) override {
    // isAuthenticated() == true только если сопряжение прошло с вводом кода
    g_secured = connInfo.isEncrypted() && connInfo.isAuthenticated();
  }
  void onDisconnect(NimBLEClient*, int reason) override {
    g_secured = false;                     // запланировать переподключение
  }
};
static PairCb pairCb;

void hudBleInit() {
  NimBLEDevice::init("HUD");
  NimBLEDevice::setSecurityAuth(true, true, true);
  NimBLEDevice::setSecurityIOCap(BLE_HS_IO_KEYBOARD_ONLY);
  NimBLEDevice::setMTU(247);
}

bool hudConnect(const NimBLEAddress& addr) {
  NimBLEClient* cli = NimBLEDevice::createClient();
  cli->setClientCallbacks(&pairCb, false);
  if (!cli->connect(addr)) return false;

  if (!cli->secureConnection()) {          // сопряжение / шифрование
    cli->disconnect();
    return false;                          // причины — раздел 4
  }
  NimBLEConnInfo ci = cli->getConnInfo();
  if (!ci.isEncrypted() || !ci.isAuthenticated()) {   // без кода — не доверяем
    cli->disconnect();
    return false;
  }

  // Дальше — как в BLE_ACL_protocol_ru.md: найти сервис, подписаться на …0008,
  // записать список ACL в …0007. Подписываться только после этой точки.
  return true;
}
```

## 3. Первое подключение и последующие

- **Первый раз** (слот свободен): клиент вводит код, ключи запоминаются на обеих сторонах, слот занят. Следующие подключения проходят по ключам — быстро и без кода.
- **Другой клиент к занятому устройству** (например, HUD к шлюзу, где уже запомнена камера, или телефон): сопряжение не удаётся. Нужно сбросить сопряжения кнопкой BOOT (раздел 5).

## 4. Отказы и что делать

| Что видит клиент / устройство | Вероятная причина | Что делать |
|---|---|---|
| `secureConnection()` неудачно; в Serial устройства: *«слот занят — новое сопряжение не принимается»* | В слоте другой клиент (другой HUD, камера, телефон с nRF Connect) | BOOT 5 с на устройстве, затем подключиться заново |
| `secureConnection()` неудачно; в Serial: *«сопряжение не удалось»* | Разные коды в устройстве и клиенте | Сверить `BLE_PASSKEY` в обоих `secrets.h` (без ведущих нулей) |
| Сопряжение проходит всегда с первого раза, но `isAuthenticated()` ложно | Клиент заявил не KeyboardOnly либо сопряжение без MITM | Проверить `setSecurityAuth(true, true, true)` и `setSecurityIOCap(BLE_HS_IO_KEYBOARD_ONLY)` |
| Клиент потерял ключи (стёрли память, перепрошили с полной очисткой), устройство их помнит | Привязка есть только на устройстве | Ничего: при повторном сопряжении с **тем же адресом** библиотека устройства сама стирает старую привязку, нужен только верный код |
| Устройство сброшено (BOOT), а у клиента ключи остались | Привязка есть только у клиента | Ничего: библиотека клиента при ответе «ключ отсутствует» сама стирает старую привязку и повторяет сопряжение (`secureConnection()` делает одну повторную попытку). Если не помогло — `NimBLEDevice::deleteBond(addr)` и подключиться заново |
| В Serial: *«сопряжение временно заблокировано»* | 5 неудач подряд | Подождать 60 с; не делать больше 3 попыток сопряжения в минуту |
| Соединение рвётся через ~15 с | Клиент не прошёл сопряжение вовремя (не вызвал `secureConnection()`) | Вызывать `secureConnection()` сразу после `connect()` |
| Подписка есть, кадров нет | Подписались до шифрования — устройство подписку проигнорировало | Подписываться после проверки `isEncrypted() && isAuthenticated()` |
| Устройство отключает сразу после подключения | Уже подключён другой клиент | Дождаться его отключения или сбросить сопряжения |

Что показать пользователю на экране HUD при неустранимом отказе: *«Сопряжение не принято. Проверьте код доступа или сбросьте сопряжения на устройстве: удерживайте BOOT 5 с.»*

**Повторные попытки:** паузы не меньше 2 с, с ростом до 10 с; не чаще трёх попыток сопряжения в минуту.

## 5. Сброс сопряжений на устройстве

Кнопка **BOOT** (GPIO0) на **работающем** устройстве:

1. Удерживать — примерно через полсекунды светодиод начнёт **быстро мигать фиолетовым**.
2. Через **5 с** все сопряжения стираются, клиент отключается, светодиод **мигает белым** около полутора секунд.
3. Отпустить кнопку. Устройство готово к новому сопряжению.

> Удерживать BOOT только **у работающего** устройства. Если кнопка зажата в момент подачи питания или сброса, плата входит в режим загрузчика и выглядит «мёртвой» до перезапуска.

Привязки хранятся во флеш-памяти (NVS). Обновление прошивки по воздуху (OTA) их сохраняет, а прошивка по USB с опцией «Erase All Flash» стирает.

## 6. Диагностика на стороне устройства

Строки в Serial:

- `BLE: защита включена (код доступа), запомнено клиентов: N из 1` / `BLE: защита ВЫКЛЮЧЕНА (BLE_PASSKEY 0 …)` — при старте;
- `BLE: подключился …`, `BLE: канал зашифрован, клиент прошёл сопряжение` — успех;
- `BLE: слот занят …`, `BLE: сопряжение не удалось (неудач подряд: N)`, `BLE: сопряжение временно заблокировано`;
- `BLE: второй клиент — отключаю …`, `BLE: клиент не прошёл сопряжение вовремя`, `BLE: отключаю клиента без сопряжения`;
- `BLE: все сопряжения сброшены (BOOT 5 с) …`.

Светодиод состояния: прежние цвета сохраняются; **фиолетовое мигание** — идёт отсчёт удержания BOOT, **белое мигание** — сопряжения сброшены.

## 7. Проверка телефоном (nRF Connect)

1. Подключиться к устройству — телефон запросит шестизначный код. Ввести `BLE_PASSKEY`.
2. После сопряжения можно читать/писать характеристики и подписываться.
3. **Телефон занимает единственный слот.** Чтобы после проверки подключить HUD, удалите сопряжение на телефоне и сбросьте его на устройстве (BOOT 5 с).

## 8. Ограничения

- Код из шести цифр защищает от случайных подключений и любопытных, но не от целенаправленного взлома. Безопасность держится на секретности кода и на Secure Connections (в отличие от старого режима, перехваченный обмен не позволяет подобрать код офлайн; каждая попытка требует нового сопряжения).
- Библиотека устройства при повторном сопряжении с адресом, у которого уже есть привязка, стирает эту привязку и продолжает сопряжение. Это удобно (клиент, потерявший ключи, возвращается сам), но сопряжение всё равно требует верного кода.
- Прошивки камер (AI-Thinker и ESP32-S3) пока **не обновлены**: они работают с устройствами только при `BLE_PASSKEY 0`. Порядок сопряжения для них тот же, что в разделе 2.
