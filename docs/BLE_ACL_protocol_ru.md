# Поток CAN-кадров по BLE с фильтром ACL (сниффер → HUD)

Протокол сниффера начиная с прошивки **2.6.0** (защита соединения — с **2.8.0**, см. [BLE_pairing_protocol_ru.md](BLE_pairing_protocol_ru.md)) (оба варианта: Super Mini и WROOM).
Сниффер ничего не расшифровывает: он отдаёт сырые кадры CAN, которые прошли фильтр,
присланный клиентом. Расшифровка — на стороне HUD.

## 1. Сервис и характеристики

Устройство `S3-CAN-Sniffer`, сервис `A1B2C3D4-0001-41A2-9E3B-000000000001`.

| UUID | Свойства | Назначение |
|---|---|---|
| `…0002` | NOTIFY | Синхронизация времени `{millis, unixEpoch}` (камера) |
| `…0004` / `…0005` | WRITE / NOTIFY | Старый режим «один ID» — оставлен для совместимости |
| `…0006` | — | Был зарезервирован под `HudState`; при выбранной схеме «сырые кадры» не используется |
| **`…0007`** | **WRITE, READ** | **Список правил ACL** |
| **`…0008`** | **NOTIFY** | **Поток кадров, прошедших ACL** |

Полные UUID: `A1B2C3D4-0001-41A2-9E3B-000000000007` и `A1B2C3D4-0001-41A2-9E3B-000000000008`.

## 2. Порядок работы клиента (HUD)

1. Подключиться к `S3-CAN-Sniffer`.
2. **Сопряжение** (если на устройстве включена защита — `BLE_PASSKEY` не 0): `secureConnection()`, проверка `isEncrypted() && isAuthenticated()`. Порядок и обработка отказов — в [BLE_pairing_protocol_ru.md](BLE_pairing_protocol_ru.md). Без сопряжения подписки и запись ACL отклоняются.
3. **Запросить MTU 247** (у NimBLE-клиента — `NimBLEDevice::setMTU(247)` до подключения). От MTU зависит, сколько кадров влезает в одно уведомление.
4. Подписаться на уведомления `…0008` (**после** шифрования канала).
5. Записать список правил в `…0007` (запись с ответом).
6. Принимать пачки кадров из `…0008`.

Поток идёт, пока есть **и** подписка на `…0008`, **и** непустой список правил.
После отключения клиента, записавшего список, **список сбрасывается** — после
переподключения его нужно прислать заново (шаги 4–5). К устройству подключается
**один** клиент: камера и HUD одновременно к одному устройству не подключаются.

## 3. Формат списка ACL (запись в `…0007`)

```
[0x01 — версия][правило 12 байт] × N        N = 0…32
```

Пустой список (только байт `0x01`) — остановить поток. Длина `1 + 12·N`; любая
другая длина или другой байт версии — список не принимается. Прочитать `…0007`
можно, чтобы убедиться, что записалось.

Правило, 12 байт, little-endian:

| Смещение | Размер | Поле | Значение |
|---|---|---|---|
| 0 | 1 | `flags` | бит 0 `PERMIT` (1 — разрешить, 0 — запретить); бит 1 `EXT` (правило для 29-битных ID, иначе 11-битных); бит 2 `ONCHANGE` (слать, только если данные изменились); бит 3 `ANYFMT` (формат ID не важен) |
| 1 | 1 | `reserved` | 0 |
| 2 | 2 | `minIntervalMs` | не чаще одного кадра этого ID за столько мс; 0 — без ограничения |
| 4 | 4 | `id` | CAN ID |
| 8 | 4 | `mask` | 1 — бит должен совпасть с `id`, 0 — любой. Точный ID: `0x7FF` / `0x1FFFFFFF` |

**Логика как у ACL:** правила проверяются сверху вниз, решает **первое совпавшее**;
если не совпало ни одно — кадр не отправляется (неявный `deny any`). Кадр совпадает с
правилом, если формат ID подходит (`EXT` / `ANYFMT`) и `((frameId ^ id) & mask) == 0`.

`ONCHANGE` и `minIntervalMs` работают **по каждому ID отдельно**, даже если правило
покрывает диапазон ID маской.

> **Для многокадровых протоколов (BAP, ISO-TP) `ONCHANGE` и `minIntervalMs` не ставить.**
> Соседние сегменты одного сообщения могут совпадать по байтам или идти чаще интервала —
> фильтр их выкинет, и сообщение не соберётся.

## 4. Формат потока кадров (уведомления `…0008`)

```
[count: 1 байт][flags: 1 байт][кадр] × count
```

- `flags`, бит 0 — с прошлой пачки были **потери** (BLE не успевал, очередь на отправку переполнилась).
- Кадр — переменной длины, `7 + dlc` байт:

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 2 | `ts` — младшие 16 бит `millis()` сниффера на момент приёма (переполняется каждые 65.5 с) |
| 2 | 4 | `idf` — CAN ID; бит 31 — 29-битный ID, бит 30 — RTR |
| 6 | 1 | `dlc` — длина данных (у RTR 0) |
| 7 | `dlc` | данные |

Пачка уходит, когда заполнена до `MTU − 3` байт или через **20 мс** после первого кадра в ней,
так что задержка не больше ~20 мс плюс интервал соединения BLE. При MTU 247 в пачку
помещается до ~16 восьмибайтовых кадров.

`ts` нужен, чтобы восстановить порядок и интервалы внутри пачки. Полная шкала времени
сниффера — через синхронизацию `…0002` (как у камеры), если она понадобится.

### Разбор на стороне HUD (C++)

```cpp
void onFrames(const uint8_t* p, size_t len) {
  if (len < 2) return;
  uint8_t count = p[0];
  bool lost = p[1] & 0x01;
  size_t off = 2;
  for (uint8_t i = 0; i < count && off + 7 <= len; i++) {
    uint16_t ts;  memcpy(&ts, p + off, 2);
    uint32_t idf; memcpy(&idf, p + off + 2, 4);
    uint8_t  dlc = p[off + 6];
    if (off + 7 + dlc > len || dlc > 8) break;          // защита от мусора
    bool     ext = idf & 0x80000000u;
    bool     rtr = idf & 0x40000000u;
    uint32_t id  = idf & 0x1FFFFFFFu;
    handleCanFrame(id, ext, rtr, p + off + 7, dlc, ts); // декодер HUD
    off += 7 + dlc;
  }
}
```

## 5. Пропускная способность

- Вся шина I-CAN — порядка 1500–1700 кадров/с. Целиком её по BLE не прокачать, и это не нужно.
- Список из примера с `ONCHANGE` даёт единицы–десятки кадров в секунду плюс BAP-навигацию только при её активности — нагрузка на BLE минимальная.
- Если BLE не успевает: в пачке выставляется бит потерь, в Serial сниффера раз в минуту строка `[STAT] BLE ACL: …`, в `errors.log` — запись о потерях. Лечится сужением списка, `ONCHANGE` или `minIntervalMs`.
- На запись логов на SD фильтр не влияет: он работает после постановки кадра в очередь записи, 32 сравнения по маске на кадр — пренебрежимо мало.
